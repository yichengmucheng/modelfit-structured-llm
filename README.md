# ModelFit · 结构化大模型建模平台

[![GitHub](https://img.shields.io/badge/GitHub-yichengmucheng%2Fmodelfit--structured--llm-181717?logo=github)](https://github.com/yichengmucheng/modelfit-structured-llm)

> 把预训练表格大模型做成分析师可自助使用的风控建模产品：分钟级出基线模型，标准化模型包跨平台迁移后打分零误差，客户通过实时 API 调用信用分。

ModelFit（内部称**百擎**）面向金融风控分析师。它用表格上下文学习替代传统评分卡 / 树模型的「特征工程 + 调参 + 数周上线」，把 **数据准备 → 建模 → 评估 → 发布 → GPU 推理部署 → 客户 API 打分** 收成一条可审计的产品链路。

---

## 产品一句话

分析师上传样本、选择「简单 / 复杂」，几分钟得到可评估、可发布、可在 GPU 生产侧稳定打分的风控模型；跨平台交接不再靠口头约定，而是靠 **1 个模型文件 + 5 个自描述契约文件**。

---

## 解决什么问题

| 痛点 | 1.0 现状 | ModelFit 2.0 |
|------|---------|--------------|
| 建模门槛高、周期长 | 评分卡 / XGBoost 依赖资深数据科学家，单模型数周 | 预训练 Transformer 将训练数据当作上下文，无需梯度训练，分钟级出基线 |
| 模块各自为政 | 训练、验证、在线推理、发布分散在多个入口 | 工作台 + 引导式四步：上传样本 → 训练 → 验证推理 → 发布 |
| 跨平台交接断裂 | 训练侧（CPU 百擎）只交一个 `.pkl`，特征顺序、正类定义靠口头同步 | LDM 标准模型包：特征契约 / 环境快照 / 金标准用例 / 评分映射 / 分数回归 |
| 分值事故风险 | 正类填反 → 高风险用户反得高分；float32 与 bf16 偏差约 `6e-3`，信用分可跨 4–6 个桶 | `positive_class` 硬拦截；SHA-256 三重校验；先量化再映射；金标准用例自主回归 |

目标场景：贷前准入、贷中监控、贷后催收。对外形态是单笔实时 `POST /score`。

## 给谁用

- **风控分析师**：零算法门槛完成建模、看 Test 集 AUC / KS / LIFT、发布模型
- **推理平台（百基）研发**：按契约加载模型，自主做合规校验与一致性验收，不需要算法同学在场
- **商务 / 合规**：部署登记、版本锁定、上线可回滚、全链路可审计
- **调用方客户**：按特征契约传 ExtData，拿到整数信用分或违约概率

## 产品全景：四系统六环节

```
画像 / 样本数据
    → 百擎 ModelFit（CPU 训练，fit = 上下文缓存）
    → 产出 LDM 标准模型包
    → 百基 GPU 推理平台（加载 base，高并发实时打分）
    → 部署登记（客户 / 合规信息）
    → 产品上架
    → 客户 API：POST /score
```

训练侧和推理侧是两种运行模式、两套负载（低频交互 vs 高并发实时），因此做成 CPU / GPU 双平台。**迁移的本质是「把训练侧产出的模型包交给推理侧加载」**，不是把已训练模型改回未训练底模。

## 分析师怎么用（主路径）

```
工作台
  ├─ 新建模型 / 上传样本 / 查看已上线模型
  └─ 近期模型动态

模型管理
  项目列表 → 模型列表 → 四步引导
    ① 选择训练样本     新上传 CSV/XLSX，或从样本库复用
    ② 模型训练         复杂度：简单(快) / 复杂(稳)；只展示 Test 集指标
    ③ 验证推理         同页双 Tab：有 Y 做评估，无 Y 做在线打分
    ④ 发布             可选评分拉伸（300–999，高分拒绝 / 高分通过）
```

- **新建模型**：步骤顺序锁定，未完成的步骤不可跳。
- **已有模型**：步骤自由跳转，卡片上可直接「查看结果」或「验证推理」。
- 导航只有三项：**工作台 / 模型管理 / 样本管理**。

模型生命周期（合规抓手）：

```
未推理 → 推理中 → 已推理 → 评估中 → 已评估
                              → 发布中 → 已上线
                                      → 已驳回
                              → 已下线 → 已删除
```

已上线版本由审批锁定，可审计、可回滚。

## 为什么这套交互长这样

表格基础模型的 `fit` **不更新权重**，只是把业务训练数据缓存成 Transformer 的 prompt。产品规则必须跟着这个算法本质走，而不是套用传统机器学习后台的惯例。

| 决策 | 原因 |
|------|------|
| 只展示 Test 集 AUC / KS / LIFT | 没有梯度训练，「训练集指标」会系统性高估效果 |
| 「训练样本」改称 **提示样本** | 它是喂给模型的上下文，不是用来更新参数的训练集 |
| 超参数收成「简单 / 复杂」 | 对应 `n_estimators = 1 或 4`，分析师不需要对着集成次数调参 |
| 验证 + 推理合并为同页双 Tab | 两者只差「有没有 Y 标签」 |
| 验证集比例可为 0 | 最终交付时可全量 fit、不出离线指标 |
| 评分函数先量化再映射 | 消掉 fp32 / bf16 尾数导致的分值跳桶 |

## LDM 标准模型包（核心交付物）

一个可迁移的离线模型 = **pkl 本体 + 部署契约**。pkl 里是预训练 Transformer 引用 + 缓存的提示样本 + 预处理管道，**不含**特征顺序、正类含义、打分公式、环境版本。这些必须 sidecar 化。

```
raw/credit_risk_tab2.5_n1_f20_800/
├── credit_risk_tab2.5_n1_f20_800.pkl   # 模型本体
├── io_schema.json                      # 特征顺序 / 类型 / 正类定义
├── source_meta.json                    # 环境快照 + SHA-256
├── test_cases.json                     # 金标准 I/O，迁移后自主回归
├── score.py                            # 概率 → 整数分（可选）
└── score_test.json                     # 打分回归用例（有 score.py 则必配）
```

目录名是给人看的档案编码：`业务场景_架构版本_集成数_特征数_样本行数`。地面真相以 `source_meta.json` 为准。

### 五个契约文件分别防什么

| 文件 | 挡住的事故 |
|------|-----------|
| `io_schema.json` | 特征列顺序写错、类别编码不一致、正类填反（高风险用户得高分） |
| `source_meta.json` | 静默换了 Python / PyTorch / 模型版本还继续打分 |
| `test_cases.json` | 目标平台加载成功但结果已经漂了，却无人知晓 |
| `score.py` | 概率到 300–999 分的映射在两边各写一套 |
| `score_test.json` | 映射系数搬过去后分值对不上 |

校验规则：

- **SHA-256 三重一致**：pkl 文件本体 ↔ `source_meta.pkl_sha256` ↔ `test_cases.generated_with.pkl_sha256`
- **正类硬拦截**：`score.py` 必须使用 `io_schema.outputs.positive_class`
- **精度容差**：float32 要求概率零误差；bf16 允许 ±0.006，但业务判断标准是「整数分是否跨桶」
- **评分纯函数**：保序、有界、无副作用；`mode='L'` 高分高风险，`mode='H'` 高分低风险（内部先 `p = 1-p`）

分析师只负责保证 5 个生成函数的**业务语义**正确（正类含义、真实样例）；引擎自动填特征名、形状、哈希和环境版本。

## 技术原理（产品需要懂的那一层）

```
传统机器学习
  训练数据 → 梯度下降更新权重 → 再对新样本推理
  每个业务场景都要重新训练，耗时以天计

表格上下文学习（In-Context Learning）
  预训练 Transformer（已在海量表格任务上训练好）
      ↓
  fit(X_train, y_train)     不更新权重，把样本当 prompt 缓存
      ↓
  predict_proba(X_test)     一次 forward pass，带上下文直接推理
```

这套机制匹配风控的真实形态：**中小样本（数千到数万行，上限约 5 万行 / 700 维）、高频迭代、先验证业务方向再决定是否精调**。推理是确定性的 forward，没有生成式采样随机性；真正的不一致来自精度、设备、依赖版本——所以环境快照和金标准用例是产品，不是附属文档。

底层模型使用开源表格基础模型 [TabPFN](https://github.com/PriorLabs/TabPFN)（Prior Labs）。本仓库是在其之上的**建模平台、交付规范与跨平台一致性方案**，不是对 TabPFN 本身的再实现。

## 质量与上线标准

全链路测试覆盖 API → 取数 → 特征 → 推理 → 封装，而不是只压模型层：

- 性能：单请求基准、阶梯升压、8 小时长稳、极限、突发流量、多模型共卡
- 一致性：单实例 / 跨时间 / 多实例 / 多 GPU / 高并发，验收 **Score 一致率 100%**，float32 下概率误差 `< 1e-6`
- 回归：黄金样本在引擎或 CUDA 升级后零漂移
- 生产口径：错误率 `< 0.1%`，关注 P99；单卡部署数量与 P99 `< 200ms` 作为容量边界

## 产品原则

1. **把算法特性翻译成产品规则**：无训练指标、提示样本、简单/复杂二选一。
2. **把工程风险翻译成交付契约**：精度差 → 金标准 + 量化打分；口头交接 → 自描述文件 + 自动校验器。
3. **把合规要求翻译成状态机**：审批锁版本、哈希防篡改、上线可回滚。
4. **Demo 跑通 ≠ 生产可上线**：先用全栈 Demo 对齐认知，生产侧按 GPU 部署 + 合规校验并行推进。
